# Рев'ю попередньої версії форми та що змінено

Предмет рев'ю: файл «ТЕСТ Swiss — Актуалізація даних» (один HTML ≈ 1,5 МБ: форма + pdfmake 0.3.11 + шрифти eUkraine у base64). Версія 2 переписана з нуля; нижче — знахідки по старому коду й рішення в новому.

## 1. Безпека та приватність

| № | Знахідка у версії 1 | Ризик | Що зроблено у версії 2 |
|---|---|---|---|
| 1.1 | Дані форми зберігалися у PDF як **клікабельне посилання** `https://dani.invalid/v1#<base64>` у футері кожної сторінки. | Випадковий клік у переглядачі відкриває браузер із «посиланням»; частина переглядачів/месенджерів показує URL у підказці; домен `.invalid` не резолвиться, але сам підхід — хак, а не механізм зберігання. | Дані зберігаються **двічі штатними засобами PDF**: як вкладений файл `data.json` (EmbeddedFiles, видно в Acrobat як вкладення) і як рядок у словнику Info (`FormData: DANIFORM2:<base64url>.<crc32>`), без жодних посилань. Є контрольна сума для виявлення пошкодження. Старі PDF (v1) читаються й далі — міграція автоматична. |
| 1.2 | **Немає Content-Security-Policy**. Будь-який вбудований скрипт виконується. | Якщо хтось підмінить файл у групі (додасть `<script>`), жодного бар'єра немає. | У `<head>` зібраний CSP: `default-src 'none'; script-src <sha256 трьох вбудованих скриптів>; style-src 'unsafe-inline'; img-src data: blob:; font-src data:; connect-src 'none'; form-action 'none'; base-uri 'none'`. Сторонній або змінений скрипт не виконається; мережевих запитів бути не може. Хеші обчислюються під час збірки, тому «підправити руками» dist не вийде — треба перезбирати (це свідомо). |
| 1.3 | Дані з PDF підставлялися у `value` полів — безпечно; але структура даних з файлу **не перевірялась** (`d.points` міг бути чим завгодно, `fill()` падав у `catch` з узагальненим повідомленням). | Низький; нечитабельні помилки. | `normalizeData()` приймає лише відомі ключі, приводить усе до рядків, обрізає списки до 50 елементів, очищає значення прихованих полів; `parsePayload()` перевіряє конверт, версію схеми, тип. Файл > 512 КБ даних відхиляється. Повідомлення про помилки конкретні. |
| 1.4 | Поля-месенджери не мали явних обмежень на вміст (посилання, довільний текст). | Сміттєві дані в контактах чергових. | Для кожного виду поля є нормалізація + перевірка (телефон → `+380 67 123 45 67`, Element без `@` і сервера, Signal/Discord за шаблоном, позивний без телефонів/посилань, назва підрозділу у верхньому регістрі до 12 символів). |
| 1.5 | Підказки про канал передачі: «лише через Element» — текстом у формі. | — | Лишено (рішення замовника) і продубльовано: у вступі, на кроці перевірки, у червоній плашці на першій сторінці звіту. |
| 1.6 | Жодного збереження чернетки: закрив вкладку — втратив усе. | Люди зберігали неповні PDF і пересилали їх. | Автозбереження чернетки у `localStorage` пристрою (TTL 7 днів, кнопка «Очистити» видаляє), плюс явна **«Чернетка PDF»** з водяним знаком «ЧЕРНЕТКА — не для подання», яку можна відкрити пізніше. **Компроміс приватності:** координати лежать у сховищі браузера на пристрої медика до 7 днів. Якщо це неприйнятно — вимкнути одним рядком (`DRAFT_TTL_DAYS = 0`) або перейти на `sessionStorage`. |
| 1.7 | Усе працює офлайн, зовнішніх запитів немає. | — | Так само; тепер це ще й гарантовано CSP (`connect-src 'none'`). Перевіряється тестом збірки (жодного `<script src>`/`<link href>`). |

## 2. Якість коду (версія 1)

- Одна сторінка ≈ 540 рядків JS без модулів і тестів; схема полів (`SECTIONS`) змішана з розміткою та PDF-логікою; `REQUIRED` — окремий список, який легко розійшовся б зі схемою.
- Валідація лише на рівні окремого поля; жодних перехресних звірок; завантаження дозволялося попри помилки («Все одно завантажити PDF?»).
- Дата бралася з `toISOString()` → у вечірні години за Києвом ставилась «завтрашня» дата (UTC). Виправлено (`todayISO` у локальному часі).
- Генерація плаката — у тому ж файлі для підрозділів (непомітна кнопка внизу), що суперечило процесу.
- Замінник у `String.replace` для склеювання файлів (у нашій першій збірці) ламався на `$&` усередині pdfmake — тепер використовуються функції-замінники; у збірці є перевірка дублювання імен між модулями та тест на залишки `import/export`.

Версія 2: `src/shared/*` — чиста логіка без DOM (схема, валідація, кодек, побудова PDF), окремо `src/form` і `src/med`; 29 юніт-тестів (`node --test`) і наскрізний Playwright-тест (заповнення через UI → звіт → повторне відкриття → плакат).

## 4. Нові дані (для кожної точки передачі)

- **НРК**: Є/Немає → кількість, РЕБ / камера / мікрофон (Так/Частково/Ні), уточнення. Звірка: за одного НРК «Частково» заборонено.
- **Гіпотермія**: хімічні грілки, спальники, Ready-Heat — кожне Є/Немає; необов'язкове уточнення кількості.
- **Хімзахист**: Є/Частково/Немає; за «Частково» уточнення обов'язкове.

У звіті: колонки у «Зведенні по точках» з кольоровими позначками, детальні рядки по кожній точці, автоматичний розділ «Потреби та зауваги» (усе червоне в одному місці). На плакаті — колонка «НРК» (кількість + що є з обладнання).

## 5. Перехресні звірки («підйобування»)

Помилки (блокують): дата в майбутньому; однакові назви точок/позицій; усі чотири месенджери чергового «Немає»; НРК = 1 і будь-яка ознака «Частково»; підготовка без жодного рівня й без «Інше»; недопустимі значення; задовгі тексти.

Зауваження (треба підтвердити галочкою): даті понад 45 днів; однакові координати двох точок; координати поза зонами 34–37 / смугами T–U (не схоже на Україну); однаковий WhatsApp у всіх трьох чергових; «забезпечені повністю», але «є потреба» (і навпаки); понад 4 години від запиту до скиду.
